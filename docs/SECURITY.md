# Isolation boundary and threat model

Generated HTML/JS is untrusted. The Python API stores and statically validates strings; it never executes game JavaScript. No `eval` or code-execution service is used for generation. Validation requires a complete bounded HTML page, canvas, inline classic scripts, keyboard controls, animation and restart markers. It rejects resource links, frames, objects, forms, event-handler attributes, navigation/storage/network/dynamic-execution API names and secrets known to the server. These checks reduce accidental unsafe output. Regex/HTML parsing is **not a JavaScript security sandbox**, and obfuscated code can evade static patterns.

The participant and judge applications never put generated HTML into `innerHTML`, `srcdoc`, blob URLs, application routes or application-origin script elements. Only a short-lived HMAC-signed URL for an authorized saved version is returned. The iframe has exactly `sandbox="allow-scripts"`, no `allow-same-origin`, no popups, forms, downloads, top-navigation or storage grants. No trust is assigned to game postMessages; there is no privileged message bridge.

The game document is fetched from a **separate cookieless hostname**. The production configuration refuses the application hostname as a preview hostname; a separate registrable site is preferred for browser process/site isolation. Local development uses `localhost` for the app and `127.0.0.1` for games, so host-only app cookies do not travel to preview. Different ports alone do not isolate cookies.

The preview container has no API keys, admin password hash or app session secret and serves only health and signed read-only game documents. SQLite is mounted read-only. It contains all stored event data, so a server exploit in that process could still read the database; signed routes and minimal code narrow exposure, but this is not database-per-team isolation. Run as an unprivileged user on a read-only filesystem with resource limits. Never place a generic file browser or admin endpoint on preview.

Each game response has CSP `default-src 'none'`, inline scripts/styles only, `connect-src 'none'`, no worker/frame/object/base/form capabilities, data-only images/media, `sandbox allow-scripts`, and app-only `frame-ancestors`. The parent app’s CSP permits frames **only** from the configured game origin; preserve it to restrict frame navigations as well. This combination is stronger than an iframe attribute alone. No script-eval permission is granted. Preview Host is checked. Signed tokens expire, never appear in application referrers and are not logged by the preview server. Anyone who obtains an unexpired preview token can play that version; do not treat the URL as permanent private authentication. Downloads instead require app session authorization and are forced attachments with `application/octet-stream`, nosniff and sandbox CSP.

Games are intended to use no network after export. Exported files cannot retain HTTP response sandbox restrictions when opened locally, so validation rejects obvious network/navigation behavior and prompts request dependency-free code. A malicious downloaded HTML file can still exercise capabilities of its local browser context; never open arbitrary manually edited imports outside an isolated browser profile. Organizers should inspect unexpected content. This is not a general-purpose safe HTML hosting service.

Browser limits: CSP is not a complete guarantee against every possible covert channel/browser vulnerability. Inline code may consume CPU/GPU/memory or loop indefinitely. No ordinary iframe can reliably meter all client resources. Separate sites encourage process separation, but behavior depends on browser and deployment. Keep games small, use bounded entities, maintain patched browsers, allow stopping/restarting a preview, and refresh/close a hung tab if needed. Browser smoke tests are run by test tooling, not by executing game code in the backend. Human gameplay testing remains necessary.

# Authentication and API boundary

Local convenience access: the launcher injects only a hash and expiry for a random one-use organizer capability into the API process. The bearer is opened in a URL fragment, removed immediately by the frontend, and exchanged for the normal HttpOnly/CSRF-protected admin session. It is valid for ten minutes, consumed once, restricted to a loopback client and loopback app origin, and disabled outside development. Never share the launcher link. The participant entrance cannot mint organizer links.

The organizer-only Connect AI form accepts credentials over the application session and CSRF boundary. It never returns a saved key, logs it in an audit event or includes it in exports. Private runtime configuration is stored separately from game data (`data-private/` locally, backend-only `/config` in Compose) with restrictive file permissions. Preview has no mount for it. Protect the host/account and backup this directory as sensitive material; keys are not encrypted against an attacker who controls the server OS. Environment configuration remains supported. One API worker is required for immediate in-memory updates.

Team codes are cryptographically random, stored as HMAC-SHA256 with an organizer secret (not raw SHA of a guessable label). Login has SQLite-backed per-IP rate limits. Codes confer team access and should be shared only within that team. Code rotation revokes all team sessions. Organizer password is Argon2 hashed via pwdlib. There is no default organizer password in the application; only isolated browser-test servers have a documented test credential.

Sessions use random 256-bit opaque HttpOnly host-only SameSite=Strict cookies, store only token hashes in SQLite, expire after a configured period and use Secure cookies in production. Mutations require an exact allowed Origin plus a session CSRF header. No application CORS access is enabled for preview. Version/request endpoints enforce ownership, including download and preview-signing routes. Admin checks protect all event settings, teams, cost reconciliation, imports, inspection, gallery and exports. Generation and starter selection have per-team rate limits and body/prompt limits.

The API uses short SQLite immediate transactions for quota/budget/concurrency/team-lock checks. The ledger’s idempotency uniqueness is scoped to team and request key; reusing a key with a different prompt is rejected. Retry with the same key after a lost response. A failed attempt creates no version; a successful file is inserted and allowance charged atomically. Past files are immutable; restoration changes a pointer only. Submissions snapshot one owned version and prompt history, and deadline/freeze checks are server-side.

No provider secret is sent to the browser or included in prompts. Provider errors shown to participants are normalized rather than raw SDK responses. Internal system instructions and credentials are not dashboard data. Unexpected server exceptions are logged server-side; protect logs and never enable verbose provider HTTP payload logging. JSON exports contain personal/team creative data and game code; restrict access, retention and backups.

# Required deployment checks

Verify HTTPS and Host forwarding, independent secrets, current models/prices, real billing limits, host-only Secure session cookie, exact parent/child CSP headers, no session cookie on game requests, read-only preview volume, no preview API routing, private environment file, persistent disk, clock sync, graceful shutdown and an off-host backup. Do not put a CDN script injector, analytics tag, wildcard CSP or cookie-setting middleware on the game origin. Dev Vite permits inline development refresh code and is never the production server. Secrets and provider choices must be reviewed before event launch.
